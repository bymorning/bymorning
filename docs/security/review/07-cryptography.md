# Cryptography Inventory and Key Management

All in-image cryptography runs on the RHEL 9 OpenSSL FIPS Provider, FIPS 140-3
CMVP certificate #4857. The runtime image (Red Hat UBI 9, Node.js 22 minimal)
links Node against the system OpenSSL and activates the provider image-wide
through `OPENSSL_CONF`; the process does not start if the validated module
cannot be loaded. The image gate (SEC-IMG) verifies FIPS mode, the active
provider, approved algorithms, and refusal of TLS 1.1, ChaCha20, and Ed25519.
The same image runs on both installers. Cloud-side cryptography (AWS KMS, S3,
RDS, Secrets Manager, CloudWatch; Azure Key Vault, Storage, PostgreSQL) is
provided by the cloud service and inherited.

The Cipher envelope names the key that wrapped it. The AWS backend refuses any
envelope whose key identity is not the configured key ARN before calling KMS,
and `Decrypt` always names the configured ARN. The Azure backend refuses a URL
from another vault or key name and selects the key version named in the
envelope. A backend that cannot unwrap fails closed (SEC-CRYPT).

## 7.2 Key management (3.13.10)

The AWS installer creates one customer-managed KMS key per installation, with
annual automatic rotation and a 30-day deletion window. It encrypts the
database, bucket, runtime secret, and log groups, and wraps Cipher data keys.
IAM conditions, not separate keys, split its use:

| Principal | Allowed use of the key |
| --------- | ---------------------- |
| Task role, storage | Encrypt, decrypt, and generate data keys only through S3 in the deployment Region (`kms:ViaService`) |
| Task role, Cipher | `GenerateDataKey` and `Decrypt` only with encryption context `bymorning=cipher` |
| Execution role | `Decrypt` only through Secrets Manager, to read the runtime secret at task start |
| CloudWatch Logs | Only for the application and PostgreSQL log groups |

The key policy delegates to the account root, so IAM policies in the account
can grant use; the customer names key administrators and restricts that
delegation (§6.1). Automatic rotation keeps earlier key material under the
same ARN, so nothing is re-encrypted. Scheduling the key for deletion makes the
database, snapshots, bucket objects, and stored Credentials unrecoverable once
the window ends.

The Azure installer creates one Key Vault RSA key (3072-bit by default;
RSA-HSM with the premium SKU) limited to wrap and unwrap. Key Vault creates a
new version every 18 months, and each version expires after 2 years. Expired
versions still unwrap but cannot wrap, and the Gateway uses the latest version
after a restart. The vault uses RBAC authorization, 90-day soft delete, and
purge protection.

Infrastructure secrets are generated by Terraform, application tokens by the
CSPRNG. No key material appears in the image or in logs. On AWS, secrets are
ECS container secrets, never plain task-definition environment. On Azure they
are a Kubernetes Secret, and the Key Vault Secrets Store CSI driver is
available as an option. Generated secrets are also in Terraform state on both
installers.

Rotation procedures and blast radius are in §14.5. Per-session and
administrative Login Session revocation is the routine mechanism, and
`WEB_COOKIE_KEY` rotation is the global break-glass. Changing the Cipher key
backend or pointing it at a different key makes every stored Credential
unreadable, so the key is fixed for the life of an installation.

An evaluation installation's local master key (`CIPHER_KEY`) is an
operator-held secret with no rotation, revocation, or usage logging. It is
outside the scope of this key management statement and of any CUI
deployment (§6).

## 7.3 FIPS posture

| Layer | Status |
| ----- | ------ |
| Load balancer TLS (AWS) | FIPS TLS policy whenever FIPS endpoints are on, which is always in AWS GovCloud (US). Outside US Regions the standard TLS 1.2–1.3 policy applies. |
| Ingress TLS (Azure) | The customer's ingress controller; its TLS configuration is the customer's to approve. |
| Application runtime cryptography (rows 2, 5–9, 12) | FIPS 140-3 validated: RHEL 9 OpenSSL FIPS Provider, CMVP #4857, verified in the shipped image (SEC-IMG). |
| AWS SDK and Bedrock endpoints | The AWS installer sets `AWS_USE_FIPS_ENDPOINT`; the image refuses a `us-gov-*` Region without it. With it set, S3, KMS, and AgentCore use their `-fips` hostnames, and Bedrock Converse uses `bedrock-runtime-fips.<region>.amazonaws.com` (SEC-FIPSEP). Bedrock Mantle has no FIPS endpoint and keeps its standard hostname with a startup notice (§12). |
| Azure nodes | `fips_node_pools` enables FIPS node images for the system and user pools; the Kata sandbox pool cannot be FIPS-enabled. The Gateway image's FIPS posture does not depend on the node. |
| Cloud services | FIPS 140 validation of AWS and Azure service endpoints is per each provider's compliance documentation and is inherited. |
